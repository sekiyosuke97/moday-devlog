# Claude Code から Codex へ — 変わり続けるために、環境ごと乗り換える

## Claude Code で作ったブランドを、Codex に移してみる

MODAY は、かなりの部分を Claude Code で作った。

Shopify のテーマ調整、Gelato 連携、9言語ブログ配信、チャットbot、
GA4 を見ながらの改善提案、記事のローカライズ。
自分がまだ分かっていない技術領域も含めて、
Claude Code に投げて、動かして、直して、ここまで来た。

別の記事で「Claude Code の使い方」も書いた。
整理しない、任せる、ノリでやる。
それが自分には合っていたし、実際に立ち上げフェーズではかなり機能した。

そのうえで、今は MODAY の作業環境を **Codex に移そうとしている**。

理由は、Claude Code がダメだったからではない。
むしろ逆で、Claude Code はかなり良かった。
だからこそ、ここで一回、乗り換えられるかを試しておきたかった。

## ひとつの環境に依存したくない

一番大きい理由はこれ。
**乗り換えられる状態でいたい**。

AI 周りの進化は、まだ速すぎる。
数週間前までの最適解が、次のリリースで普通に変わる。
昨日まで「このツールが一番強い」と思っていても、
今日になったら別の環境の方が、今やりたい作業に合っていることがある。

この速度の中で、ひとつの環境に深く依存するのは少し怖い。
もちろん、使い込むことで得られる強さはある。
プロジェクト文脈、設定ファイル、ワークフロー、手癖。
それらが溜まるほど、作業は速くなる。

でも同時に、移れなくなる。

AI 駆動型のブランドをやるなら、
道具の変化に合わせて、自分の運用も変えられる必要がある。
Shopify でも、Gelato でも、Render でも、Make.com でも同じだった。
その時点で合うものを選び、合わなくなったら組み替える。

なら、AI 開発環境も同じように扱うべきだと思った。

## 構築フェーズから、運営フェーズに入った

もうひとつの理由は、MODAY のフェーズが変わったこと。

立ち上げ前は、とにかく構築だった。
ストアを作る。商品を並べる。翻訳する。注文フローをつなぐ。
ブログ配信パイプラインを作る。チャットbot を置く。

このフェーズでは、Claude Code がかなり強かった。
コードを書いて、ファイルを読んで、構成を整理して、
必要なものをどんどん実装していく。
「まず動かす」ための力がすごくあった。

ただ、今から増える作業は少し違う。

UI 改善。
商品ページの見せ方。
ブログのアイキャッチ。
SNS 投稿。
ショート動画の構成。
モデル画像。
広告ではなく、フィードで一瞬止まってもらうためのクリエイティブ。

ここから先は、コードだけでは足りない。
**見た目、言葉、画像、文脈、引っかかり** の比重が上がる。

その領域では、Codex の方が合いそうだと感じた。
特に Image 2.0 の画像生成は、かなりクオリティが高い。
開発も今やっている範囲では不自由を感じていない。
なら、運営フェーズの作業環境として試す価値がある。

## Claude Code は、普通に良かった

ここはちゃんと書いておきたい。
Claude Code から移るからといって、Claude Code を否定したいわけではない。

基本、何でもできた。
少なくとも MODAY の立ち上げでは、Claude Code がいなければここまで来ていない。

最近リリースされた `/workflows` も、本当にクオリティが高かった。
あれはかなり良い。
作業の流れを定義して、繰り返し使える形にする。
開発規模が大きくなって、複数の流れを安定して回す段階では、
また使いたいと思っている。

だからこれは「Claude Code から卒業」みたいな話ではない。
必要になれば戻る。
大きめの開発フェーズに入ったら、Claude Code の方が合う場面は普通にあると思う。

ただ、今の MODAY は、巨大な開発プロジェクトではない。
構築の山は一旦越えていて、
これから必要なのは、細かい改善と、集客のためのクリエイティブを毎日出すこと。

その作業量に対して、Claude Code の MAX プランは少しオーバースペックに感じた。
かといって PRO プランだと、制限が早く来すぎる感覚があった。

その間に、Codex がちょうどよさそうに見えた。
これも正直な理由だ。

## 弱点は、画像とクリエイティブだった

Claude Code で一番違和感があったのは、画像とクリエイティブの領域だった。

コードやファイル操作、構成の整理は強い。
文章のローカライズもかなり使えた。
ただ、MODAY がこれから必要としているのは、
「きれいに動く」だけではなく、
「見た瞬間に引っかかる」ものを作る力だ。

ブログの hero 画像もそう。
SNS の一枚目もそう。
ショート動画のモデル画像もそう。
商品ページの見え方もそう。

スクロールしている人の手を止めるには、
コードの正しさとは別の判断が要る。
色、構図、視線、違和感、情報量。
そのあたりを含めて試すなら、Codex の方が今はやりやすそうだった。

実際、以前の記事でショート動画を作るために、
Codex に絵コンテを書かせ、ChatGPT Image でモデルを作った。
その時点で、集客寄りの作業では OpenAI 側のツールに手応えがあった。

今回は、その流れをもう少し進める。

## これはツール比較ではない

たぶん、この記事を「Claude Code vs Codex」として読むと、少しズレる。

自分がやっているのは、どちらが優れているかを決めることではない。
今の MODAY に、どちらが合うかを試しているだけだ。

構築フェーズでは Claude Code が合っていた。
運営と集客のフェーズでは Codex が合うかもしれない。
また開発規模が大きくなれば、Claude Code に戻るかもしれない。
別の環境が出てきたら、そこに移るかもしれない。

それでいいと思っている。

MODAY は、最初からそういう作り方をしている。
知らない POD サービスを Claude に選ばせた。
FastAPI / Render で作ったものを、あとから外した。
Render を捨てたと思ったら、チャットbot ではまた使った。
ブログ配信も、API 翻訳から Claude Code 内の rewrite に切り替えた。

その時点で良いと思ったものを使い、
違うと思ったら、組み替える。

今回も、その延長でしかない。

## 「変化」が特別なイベントではなくなる

今回の乗り換えを、MODAY にとって何の変化かと聞かれると、
正直、あまり粒立てる必要すらないと思っている。

変化しながらやっていくことを、標準思想にしているからだ。

ストアを作って終わりではない。
記事を書いて終わりでもない。
動画を1本作って終わりでもない。
使うAIも、使うツールも、作業の分担も、どんどん変わる。

むしろ、変わらなくなったときの方が危ない。
「このやり方でいける」と思って固定した瞬間に、
環境の進化から遅れ始める。

だから、乗り換える。
試してみる。
合わなければ戻る。
合えば、そのまま進める。

それくらいの軽さでいい。

## 次にやること

Codex に移したからといって、急に何かが完成するわけではない。

やることは、地味だ。

ブログを書く。
hero 画像を作る。
商品ページを直す。
SNS 投稿を作る。
ショート動画の次の案を出す。
チャットログや GA4 を見て、改善案を出す。
1日1個、何かを良くする。

その繰り返しの中で、Codex がどこまで使えるかを見る。

もしうまくいけば、MODAY の運営フェーズは Codex 中心で回る。
もし合わなければ、また変える。

大事なのは、どのツールを使うかではなく、
**変えられる状態でいること**。

AI 駆動型ブランドをやるなら、
AI との付き合い方そのものも、固定しない方がいい。

それでは、また書きます。
