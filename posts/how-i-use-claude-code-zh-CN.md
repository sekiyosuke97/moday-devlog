# 我是怎么用 Claude Code 的 —— 不整理、交出去、凭直觉干

## 回头梳理一下，我到底是怎么用 Claude Code 的

到目前为止，我写了不少关于 MODAY 怎么搭起来的事，
但「**我到底是怎么操控 Claude Code 的**」这一块，一直没写过。

选技术栈的事、搭分发流水线的事、
9 种语言本地化的事、15 分钟做出客服 bot 的事，
全都站在「**做了什么**」这一侧。

店开起来了，进入运营阶段了，
就在这里换个视角，从「怎么用」的角度写一下。
先把结论摆出来：**不整理、交出去、凭直觉干**。

外面大部分 Claude Code 的用法介绍，方向上大概跟我是相反的。

## CLAUDE.md 是 Claude 自己写的

外面常听到的说法是：「**把项目信息整理好，写进 CLAUDE.md**」。
品牌信息、技术栈、代码规范、优先级。
为了让 Claude Code 能掌握项目上下文，人得先把这些整理出来。
这算是比较标准的用法。

而 MODAY 的 CLAUDE.md，**没有一行是我自己写的**。
里面写了什么，我也没仔细看过。

搭建初期，我跟 Claude Code 说了一句「这个文件你自己整理就行」，
它就开始自顾自地把品牌信息、技术栈、SKU 表、Markets 设置、
每个 Phase 的优先级，全部码进去。偶尔翻一眼，
大概率比我自己手动整理的版本更适合 Claude 来读。

从头到尾，我没参与过任何「整理」这件事。
**整理这个动作本身，已经被我交给 Claude 那边了**。

## Session 怎么切分？凭感觉

Session 是有切分的，不过**没有规则**。

我没有按目的严格划分，大致就是
「内容制作」「UI/UX 优化」「MD（杂七杂八的活）」
这种粗颗粒的归类在跑。
图像生成、翻译、写代码，全都可以在同一个 session 里混着干。

我不会按「翻译 session」「写代码 session」这种角色去拆。
**我按工作流本身拆**。
划分方式很糙，但结果是「灵感能一个接一个连上」。

在调 UI 的时候，突然想到「啊这个改动配套的翻译也得改一下」，
就直接在同一个 session 里把翻译也跑了。
跨 session 携带上下文的成本是零，
所以**判断的流不会被切断**。这个意外地很关键。

## 技术细节，我基本不指挥

之前在另一篇文章里也写过，选技术栈的阶段，我一条技术条件都没提。
我提的全是业务侧的要求。
进入实施阶段之后，这个姿态也没变。

唯一刻意强调的一条是：
「**Shopify 和 Gelato 请按标准用法来用，原创实现降到最低**」。

我觉得这是用 SaaS 的铁律。
在供应商预期的范围内使用，长期来看才是最稳的。
定制实现短期看很诱人，但每次供应商更新就会被打碎。
标准流程、标准 API、标准主题结构。
要脱离标准时，必须是真的非脱离不可的场景才行。

只要把这一条传达清楚，API 怎么调、测试怎么写、错误怎么处理、
实现的细节这些，基本可以全权交给 Claude Code。

## 它问「这个要怎么办」，我答「你自己看着办」

Claude Code 偶尔会回过头来确认：
「这个文件能给我看一下吗」「这样可以吗」
「测试要怎么写」之类的。

这些问题，我几乎全部回「**你自己处理**」。

想看文件？自己 view 一下就行。
来征求判断？我回「你自己判断」。
结果是大多数情况下，它会自己去读、自己拍板、
然后一路把实现也推到位。

这就是我在另一篇文章里写过的「**把主导权交给 AI 那一侧**」的实践。
不替它回判断，让它自己持有判断权。

剩下需要我亲手干的，只有**那些怎么都没法通过 API 推进的事**：
银行开户、支付审核、各服务的注册、付费订阅、API key 申请。
那些地方人类才能签合同，只能我自己上。
除此之外，全都搬到 Claude 那边了。

## 让它每天巡 GA4，自己提改进方案

这是开店之后才开始的新做法。

每天让 Claude Code 把 GA4 全过一遍，
**自己列出问题点和改进方案**。
我只负责看一眼，把明显跑偏的剔掉。
剩下六七成，当场让它实现。

从提案到上线之间，我做的只有 GO/NG 这一道判断。
写代码、想架构这种事，我基本不做。

我想把这个当成运营理念定下来：
「**每天一定要落地一条改进**」。
从店开起来那一刻开始，每天都比昨天好一点。
改进循环不停的品牌，长期看会更强 —— 这是我下的赌注。

而这个循环里，99% 的工作量是 Claude Code 在转。

## 不整理，却又是整理过的状态

写到这里，我又想了一下。
「整理」「设计」「计划」这种传统开发里的动作，我基本都没做。

CLAUDE.md 没写。session 凭感觉切。工作流没固化成 routine。
没有架构图，也不用任务管理工具。
就这样，从搭建到运营，居然也还是转得起来。

更准确的说法是：**整理这件事被托付给 Claude 那一侧了**，仅此而已。
我不做，但 Claude Code 在做。
所以结果上，整理过的状态一直被维持着。

这个结构，跟孙正义说一句「干吧」，
下面一支超强的执行部队就动起来，整理也好实现也好全包了，那个形态很像。
**我留在「干吧」这一侧做判断，执行部队换成了 AI**。

AI 时代，个人也能复刻这个结构出来 ——
这是我这三周下来，最大的一个手感。

## 结尾

这肯定不是「正确」的用法。
认真写 CLAUDE.md、按目的切分 session、
把工作流固化成 routine 的做法，应该也走得通。

只是对我来说，**不整理反而更快**。
与其花时间去整理，不如把活丢给 Claude Code，
然后用那段时间来判断它给出来的东西。

那就这样，回头再写。
