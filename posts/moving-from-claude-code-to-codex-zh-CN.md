# 从 Claude Code 到 Codex — 为了持续变化，连工作环境也一起切换

## 把一个用 Claude Code 做出来的品牌，搬到 Codex 里

MODAY 有相当大一部分，是用 Claude Code 做出来的。

Shopify 主题调整、Gelato 集成、多语言博客分发、聊天机器人、
基于 GA4 的改进建议、文章本地化。
有些技术层我自己还没有完全理解，
但我把任务交给 Claude Code，让它做，检查结果，然后继续往前走。

我之前也写过一篇，讲自己怎么用 Claude Code。
不刻意整理。交给它。跟着节奏走。
这种方式很适合我，在搭建阶段也确实非常有效。

但现在，我正在尝试把 MODAY 的工作环境迁到 **Codex**。

不是因为 Claude Code 不好。
恰恰相反。
正因为 Claude Code 足够好，我才想测试一下，自己是不是仍然可以切换出去。

## 我不想依赖单一环境

最大的理由是这个。
我想保持一种可以随时切换的状态。

AI 工具的变化速度仍然太快。
几周前的最佳选择，可能因为一次发布就变得普通。
昨天还觉得某个工具最强，
今天另一个环境可能更适合眼前的工作。

在这样的速度下，深度依赖一个环境会让我觉得有点危险。
当然，深入使用一个工具会带来力量。
项目上下文、配置文件、工作流、操作习惯。
这些东西积累得越多，工作越快。

但同时，也越难移动。

如果 MODAY 要做一个由 AI 驱动的品牌，
那么运营方式也必须能随着工具变化。
Shopify、Gelato、Render、Make.com 都是这样。
在当下使用合适的东西。不合适了，就重新组合。

AI 开发环境也应该用同样的方式对待。

## 搭建阶段结束了，运营阶段开始了

另一个理由是，MODAY 的阶段变了。

上线前，几乎所有事情都是搭建。
做商店。放商品。翻译页面。连接订单流程。
搭博客分发管线。加聊天机器人。

在这个阶段，Claude Code 很强。
它写代码、读文件、整理结构，
不断实现当下需要的东西。
它把事情推进到“先跑起来”这一点的能力很强。

但接下来要增加的工作，性质有点不同。

UI 改进。
商品页的呈现方式。
博客 hero 图。
社交媒体帖子。
短视频构思。
模特图。
不是广告，却能让人在 feed 里停一下的创意。

从这里开始，只有代码是不够的。
权重会转向 **视觉、语言、图片、语境和钩子**。

在这个领域里，我感觉 Codex 现在可能更合适。
尤其是 Image 2.0 的图片生成质量，已经到了我可以实际使用的程度。
开发方面，就目前的工作范围来看，我也没有明显感到不方便。
所以，把它作为运营阶段的工作环境来测试，是值得的。

## Claude Code 真的很好

这一点我想写清楚。
从 Claude Code 迁走，并不代表我否定 Claude Code。

基本上，它什么都能做。
至少 MODAY 的上线，如果没有 Claude Code，我走不到这里。

最近发布的 `/workflows` 质量也真的很高。
那是一个很好的功能。
定义工作流，并让它可以重复使用，
这正是项目规模变大、多个流程需要稳定运转时需要的东西。
如果以后再次进入更大的开发阶段，我还会想用它。

所以这不是“从 Claude Code 毕业”的故事。
需要的时候，我会回去。
在更大的开发阶段，Claude Code 可能再次成为更合适的选择。

只是现在的 MODAY，不是一个巨大的工程项目。
第一座搭建的山已经暂时翻过去了。
接下来需要的是细小的改进，以及每天用于增长的创意素材。

对这种工作量来说，Claude Code 的 MAX 计划开始显得有点过剩。
但 PRO 计划又感觉限制会来得太快。

Codex 现在看起来刚好在中间。
这也是一个很现实的理由。

## 弱点是图片和创意

我在 Claude Code 上最有违和感的地方，
是图片和创意相关的工作。

代码、文件操作、结构整理：很强。
文章本地化：也相当能用。
但 MODAY 接下来需要的，不只是“能稳定运行”的东西。
它需要的是，让人第一眼就停下来的东西。

博客 hero 图。
社交帖子的第一张图。
短视频用的模特图。
商品页看起来的样子。

让一个正在滚动屏幕的人停下来，
需要的是和“写出正确代码”不同的判断。
颜色、构图、视线、微妙的不协调、信息密度。
现在要测试这些东西，Codex 更顺手。

之前写短视频那篇文章时，
我让 Codex 写分镜，用 ChatGPT Image 做模特图。
那时我第一次感觉到，
OpenAI 这一侧的工具，可能更适合增长和创意相关的工作。

这次只是把那个方向再往前推进一点。

## 这不是工具对比

如果把这篇文章读成“Claude Code vs Codex”，其实会有点偏。

我不是在判断哪一个工具绝对更好。
我只是在测试，哪一个更适合现在的 MODAY。

搭建阶段，Claude Code 很合适。
运营和增长阶段，Codex 也许更合适。
如果开发规模再次变大，我可能会回到 Claude Code。
如果出现更合适的环境，我也可能再切过去。

这样就好。

MODAY 从一开始就是这样做出来的。
我让 Claude 选择了一个我不认识的 POD 服务。
我用 FastAPI 和 Render 做过东西，后来又撤掉。
我以为自己不用 Render 了，结果聊天机器人又把它用回来。
博客管线也从 API 翻译，切换成了 Claude Code 内部的 rewrite。

在当下使用看起来合适的东西。
当它不再合适时，重新组合。

这次也是同一件事的延长。

## “变化”不再是特殊事件

如果问这次迁移对 MODAY 来说意味着什么，
老实说，我甚至不觉得需要把它单独定义成一个大变化。

一边前进一边改变，本来就是默认思想。

商店不是做出来就结束。
文章不是发布了就结束。
视频不是发了一条就结束。
使用的 AI、使用的工具、工作的分工方式，都会继续变化。

真正危险的，反而是不再变化。
当我觉得“以后就按这个方式来”的那一刻，
我就开始落后于环境的变化速度。

所以，我切换。
我测试。
不合适就回来。
合适就继续。

这种轻度就够了。

## 接下来要做什么

迁到 Codex，并不会让什么东西突然自动完成。

要做的事情依然很朴素。

写博客。
做 hero 图。
改商品页。
做社交媒体帖子。
想下一条短视频。
看聊天机器人日志和 GA4，再把它们变成改进。
每天让一件事变好一点。

在这样的重复里，我会看 Codex 能走到哪里。

如果顺利，MODAY 的运营阶段会以 Codex 为中心运转。
如果不合适，我会再改。

重要的不是使用哪个工具。
重要的是，保持可以更换工具的状态。

如果 MODAY 是一个 AI 驱动的品牌，
那我和 AI 共事的方式本身，也不应该被固定下来。

下次再写。
