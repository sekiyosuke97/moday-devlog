# Claude Code の使い方 — 整理しない、任せる、ノリでやる

## 振り返って書いておく、Claude Code の使い方

ここまで MODAY 構築の話を書いてきたが、
「**Claude Code をどう操っているか**」は書いてなかった。

スタックを選んだ話、配信パイプラインを組んだ話、
9言語ローカライズの話、チャットbot を15分で作った話、
全部「**何を作ったか**」の側だった。

公開も済んで、運営フェーズに入ってきたので、
ここでメタ視点で書いておく。
結論を先に書くと、**整理しない、任せる、ノリでやる**。

世間でよく見る Claude Code 解説とは、たぶん逆方向の話になる。

## CLAUDE.md は Claude が書いた

世間では「**CLAUDE.md にプロジェクト情報を整理して書きましょう**」と言われる。
ブランド情報、技術スタック、コーディング規約、優先順位。
Claude Code がプロジェクトの文脈を掴めるように、人間が整理しておく。
というのが、まあ標準的な使い方。

MODAY の CLAUDE.md は、**自分で書いた行が1つもない**。
何が書いてあるかも、把握していない。

構築初期に、Claude Code に「自分でファイル整えていいよ」と言ったら、
ブランド情報、技術スタック、SKUテーブル、Markets 設定、Phase ごとの優先順位を、
勝手にまとめ始めた。たまに眺めると、自分が手で整理するより、
おそらく Claude が読みやすい形になっている。

最初から最後まで、自分は「整理」を一切やっていない。
**整理という作業そのものを、Claude 側に渡している**。

## セッションは「ノリで」分ける

セッションは分けている。が、**ルールはない**。

目的別の厳密な切り分けはやってなくて、ざっくり
「コンテンツ制作」「UI/UX 改善」「MD（雑多な作業）」
みたいな括りで動かしている。
画像生成も翻訳もコード書きも、同じセッションの中で混ぜる。

「翻訳セッション」「コード書きセッション」みたいに役割で分けない。
**作業の流れで分ける**。
雑な分け方だが、結果として「思いつきが連鎖する」状態になる。

UI を直していて、ふと「あ、これに合わせて翻訳も変えた方がいい」と気づく。
そのまま同じセッションで翻訳も走らせる。
セッション横断で文脈を持ち越すコストがゼロなので、
**判断の流れが切れない**。これが意外と効いている。

## 技術的な指示は、ほぼしない

別の記事で書いたが、スタック選定の段階で、技術条件は1つも出していない。
出したのは全部ビジネス側の条件だけ。
実装に入ってからも、このスタンスは変わっていない。

唯一意識して伝えているのが、
「**Shopify と Gelato は標準的な使い方をしてくれ、オリジナル実装は最小限で**」
ということ。

これは SaaS の鉄則だと思っていて。
ベンダーが想定した範囲の中で使うのが、長期的には一番安定する。
カスタム実装は短期的には魅力的だが、ベンダー側のアップデートで壊れる。
標準のフロー、標準の API、標準のテーマ構造。
ここから外れるときは、本当にそれが必要なときだけ。

これだけ伝えれば、API の叩き方、テスト戦略、エラーハンドリング、
実装の細部はほぼ全部 Claude Code に任せられる。

## 「これ教えて」と聞かれたら、「自分でやって」と返す

Claude Code は、ときどき確認してくる。
「このファイルの内容を見せてください」「これでいいですか？」
「テストはどう書きますか？」と。

そのほぼ全部に、「**自分でやって**」と返している。

ファイルを見たいなら自分で view を使えばいい。
判断を仰がれたら「自分で判断して」と返す。
結果、ほとんどの場合は自分で読みに行って、自分で判断して、
そのまま実装まで進めてくれる。

これは、別の記事で書いた「**主体性を AI 側に渡したい**」の実践。
判断を返さない、判断を持たせる。

最後に残るのは、**どうしても API で動かせない領域** だけ。
銀行口座、決済審査、各サービスの申込み、課金登録、API キー発行。
そこは人間としか契約できないので、自分が手を動かす。
それ以外は、全部 Claude 側に持たせている。

## GA4 を毎日巡回させて、改善提案させる

公開後に始めた、新しい運用がこれ。

毎日、Claude Code に GA4 を巡回させて、
**課題と改善案を出させる**。
自分はそれを眺めて、明らかに筋が悪いものだけ排除する。
残った 6〜7割を、その場で実装させる。

提案から実装までの間に、自分がやっているのは GO/NG の判断だけ。
コードを書くことも、設計を考えることも、ほぼゼロ。

これを運営コンセプトにしようと思っている。
「**1日1個は必ず改善を実装する**」。
ストアを開けた瞬間から、毎日1つ、何かが良くなっている状態を作る。
改善ループが止まらないブランドが、結果的に強くなる、という賭け。

そして、その改善ループの99%は Claude Code が回す。

## 整理しないのに、整理されている

ここまで書いてきて、改めて思う。
自分は「整理」「設計」「計画」みたいな伝統的な開発作法を、ほとんどやっていない。

CLAUDE.md は書いてない。セッションはノリ。ワークフローはルーチン化してない。
技術設計図もないし、タスク管理ツールも使っていない。
それなのに、構築から運営まで、なんとなく回っている。

正確には、**整理は Claude 側に任せている**、というだけのこと。
自分はやらないが、Claude Code は整理する。
だから結果として、整理された状態は維持されている。

この構図、孫正義が「やりましょう」と言うと、
超優秀な実行部隊が動き出して、整理も実装も全部やってくれる、あの形に近い。
**自分は「やりましょう」と判断する側に残り、実行部隊が AI になっている**。

AI 時代、個人がこの構図を再現できるようになった、というのが、
この3週間で得た一番の手応え。

## 結び

これは正しいやり方ではないと思う。
たぶん、CLAUDE.md をしっかり書いて、セッションを目的別に分けて、
ワークフローをルーチン化するやり方も、ちゃんと成立する。

ただ、自分の場合は **整理しないほうが速かった**。
整理に時間を使う暇があったら、Claude Code に投げて、
出てきたものを判断する時間にしたい。

それでは、また書きます。
